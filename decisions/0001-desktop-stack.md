# 0001. Desktop stack - Tauri 2, Rust core, React + TypeScript UI

## Context

Rune runs up to 16 agent CLIs in real pseudo-terminals, streams their output to a rich UI,
embeds a browser, and must ship on macOS, Windows, and Linux. It must start fast and stay
light, because the agents themselves already use a lot of memory. The reference product is
built on Tauri 2 + Rust + React, which proves the stack carries this workload.

## Decision

- **Shell:** Tauri 2. Rust core owns processes, PTYs (`portable-pty`), persistence
  (SQLite via `rusqlite`), secrets (OS keychain), and the MCP server.
- **UI:** React + TypeScript + Vite. Tailwind CSS v4 mapped to design tokens, Radix
  primitives for accessible components, zustand for state, xterm.js (WebGL renderer) for
  terminals, react-three-fiber later for Realm.
- **IPC:** Tauri commands and channels with TS bindings generated by `tauri-specta`.
- **Tooling:** pnpm, Biome (lint + format), `tsc --noEmit`, clippy + rustfmt, Vitest,
  Playwright, `cargo test`. GitHub Actions on all three OSes.
- **Layout:** `apps/desktop/` (pnpm workspace root at repo root) so a phone app and relay
  server can join as `apps/*` later without a restructure.

## Options considered

| Option | For | Against |
|--------|-----|---------|
| Tauri 2 + React | Small binaries, low RAM, Rust for PTY/perf, proven by reference | Webview differences per OS; child webviews still `unstable` |
| Electron + React | One Chromium everywhere, mature node-pty, VS Code-proven terminals | 150+ MB, high RAM per window, Node for process control |
| Native per OS | Best feel | Three codebases; impossible to keep at parity |

## Consequences

- Cross-platform webview differences (WebKit on macOS/Linux, WebView2 on Windows) must be
  tested in CI, especially xterm WebGL and fonts.
- The browser dock (F11) needs a spike on Tauri multi-webview before its spec is approved.
- Everyone touching processes or storage writes Rust; the UI stays a pure client of `ipc/`.
